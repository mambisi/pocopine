# RFC-120: Internationalization — one message format, compiled like everything else

**Status:** Draft (shape spec — not yet scoped or phased for implementation)
**Crates:** new `pocopine-locale` (leaf: `Locale`, CLDR parent chain, plural selection, MF1 formatter; host-gated extraction + codegen + number/date rendering); `pocopine-core` (`pp-t`, `$t`, router); `pocopine-macros` (extraction + validation); `pocopine-cli` (`pocopine locale`, aliased `i18n`); `pocopine-server` (request locale negotiation + user-facing error integration); `pocopine-ssr` (stamping translated text)
**Relates to:** RFC-099 (SSR parity — §4 "same text for same value" is reopened here; **phases 1–2 implemented, pending on PR #209** — which gates only the server-stamping slice of this RFC, not the rest), RFC-092 (Stylekit — the extract → catalog → compile pipeline this copies), RFC-111 (compile-time path validation), RFC-094 (comment anchors as decision carriers), RFC-119 (authority is explicit, never ambient)

## Summary

Translations are **compiled artifacts, not runtime data**. `locales/<locale>.json`
holds ICU MessageFormat 1 strings under explicit dotted keys; the build extracts
every key referenced by a `.poco` or `.rs` source, validates it against the
default locale, and emits typed Rust functions plus one compiled message catalog per locale. A
missing key in the default locale is a **compile error**, the same way a missing
field in a template is today.

Templates get one directive, `pp-t`, which owns an element's text content the way
`pp-text` already does. Rust gets generated functions that take `Locale`
explicitly. There is no ambient current-locale, no pluggable format backend, and
no second message syntax. The same Rust API serves server-function errors,
validation messages, confirmations, and recipient messages such as email or
notifications, including standalone background workers (§5.5).

The load-bearing decision is not the syntax. It is **the parity split**: plural
and select *selection* is structural, so it runs off one generated CLDR rule table
linked into both server and client; number and date *rendering* is text, so under
SSR the server's output is authoritative and merely claimed by hydration.
`Intl.PluralRules` is banned and ICU4X is not shipped to the browser at all —
measured at 11× the cost of generating the table (§6.4) — while every other `Intl`
API is used freely on the client for zero wasm bytes.

Exactly **one wasm binary** serves every locale. Messages ship beside it as one
compiled catalog per locale — a data file, not a build — so adding a locale adds
an asset and never a byte of wasm (§7.1).

## 1. Why now, and why this shape

pocopine is already a compiler. `#[component]` emits plans, RFC-111 validates
template paths at compile time, and Stylekit walks every `.poco`, extracts what
is used, and compiles a deterministic artifact with spanned diagnostics. An i18n
system that shipped a JSON blob and looked keys up at runtime would be the only
part of the framework that discovers its own mistakes in production.

The JS ecosystem has already converged on this answer. Paraglide compiles each
message to a typed function so bundlers tree-shake the rest; Angular substitutes
strings at build time entirely; Lingui and FormatJS extract from the AST. In
Rust, `leptos_i18n` is the closest prior art and gets the important thing right —
**keys, interpolation arguments, and the locale set are all checked at compile
time**. This RFC takes that guarantee as the baseline and adds the pieces
pocopine's own architecture makes cheap.

## 2. Message format: ICU MessageFormat 1, closed subset

```
{arg}                                   interpolation
{arg, plural, one {…} other {…}}        CLDR categories; =N exact matches allowed
{arg, select, male {…} other {…}}       author-declared variants
{arg, number} {arg, number, percent}    locale-sensitive rendering
{arg, date, short|medium|long}
{arg, time, short|medium}
'{' '}'                                 ICU apostrophe escaping
```

Not in the subset: `selectordinal`, number skeletons, custom formatters, message
references, nesting beyond one level. Each is an additive extension that must
argue for itself; none is a default.

**Why MF1 and not MF2.** MessageFormat 2 reached Final Candidate in March 2025
and is a stable Unicode standard, shipping in ICU4C and ICU4J. But adoption has
not started — TC39 wants roughly a dozen organisations running it in production
before advancing, and that bar is unmet in 2026, while MF1 usage in the i18next
ecosystem roughly tripled over the past year. Every TMS an author would plausibly
use speaks MF1 today. The parser is therefore isolated behind a typed AST so MF2
is a **parser swap, not a redesign**, the day the ecosystem moves.

**Why not Fluent.** Fluent's asymmetric model — a flat English string mapping to
a multi-variant translation, so translators use their full grammar without asking
a developer — is the best translator-facing design in existence. It is rejected
here for two reasons that are specific to this codebase and not a judgement on
Fluent. First, it is a *language* (terms, attributes, message references,
selectors), which is exactly what "small enumerable surfaces get a PR, not a DSL"
forbids. Second, asymmetry makes the argument set a runtime property of each
locale file, which forfeits the compile-time arg checking that is the whole point.

**Why not vue-i18n's pipe form.** `'no apples | one apple | {n} apples'` selects
by pipe *index*, not CLDR category, which is why Slavic locales need hand-written
`pluralizationRules`. Selecting by category from the start avoids inheriting that.

## 3. Keys are explicit

Lingui's generated-ID mode uses the source text as the key. It is rejected: a
copy edit silently orphans every translation, diffs become unreadable, and there
is nowhere stable to hang a translator comment or an LSP completion. Explicit IDs
stay stable when the message changes and carry meaning for translators.

Keys are flat dotted paths namespaced by module: `cart.items_in_basket`,
`auth.sign_in.submit`.

## 4. Where messages live

```
locales/
  en.json        ← default locale — this file IS the compile-time contract
  fr.json
  de.json
```

```toml
# pocopine.toml
[locale]
default = "en"
locales = ["en", "fr", "de"]
routing = "prefix-except-default"   # | "prefix-all" | "none"
```

One file per locale, flat keys, ICU MF1 values — the shape every TMS exports and
imports. Per-component message blocks (vue-i18n's `<i18n>` SFC block) are
attractive because they mirror pocopine's per-component `.poco` + `.css`
convention, but they multiply into *N components × M locales* files and break
TMS round-tripping. Module-path namespacing inside one file buys the same
locality at none of that cost.

### 4.1 Locality is enforced, with exactly one shared namespace

A key referenced from module `cart` must start with `cart.` — or with
`common.`. Anything else is a compile error.

Without enforcement the failure is invisible rather than loud: someone in
`orders` reuses `cart.checkout_button` because the English happens to match, then
`cart`'s copy changes and `orders` silently changes with it. Requiring the string
to be *moved* to `common.` makes sharing a decision somebody takes on purpose.

`common.*` is not a loophole, it is a necessity — `common.loading` is the
canonical member. Forcing `cart.loading`, `orders.loading` and `auth.loading` to
coexist hands a translator the same string four times and guarantees they drift.

Two further checks run in the same pass: **duplicate keys within a file** are a
hard error (JSON permits them and silently keeps the last), and a **leaf/branch
collision** — `"cart"` alongside `"cart.items"` — is a lint, since Rust's
separate namespaces let `mod cart` and `fn cart()` coexist but nobody should
have to know that.

### 4.2 Keeping the default-locale file mergeable

A single file that every feature appends to is a merge-conflict magnet unless it
has a canonical form. Three properties make it one:

1. **Flat keys, one per line, sorted.** Every key is an independent line, so two
   developers adding keys under different namespaces never touch the same
   region. Nested objects are what merge badly — every addition to a sub-object
   lands near the same shared braces. A conflict then means two people touched
   *the same key*, which is a real disagreement worth surfacing.
2. **The tool writes the file.** `pocopine locale extract` inserts in sorted
   position; humans do not choose placement, so they cannot fight over it.
3. **A merge driver.** Because the file has one canonical form, merging is
   mechanical — union the key sets, re-normalize, conflict only on
   same-key-different-value. `pocopine locale merge` registers in `.gitattributes`,
   which also disposes of the trailing-comma edge case that makes appending to
   JSON conflict-prone.

Non-default locales are not hand-edited at all — they arrive via
`pocopine locale import` (§9). The human conflict surface is only ever the default
locale. Teams with genuine contention may shard by top-level namespace
(`locales/en/cart.json`), which is a handful of files rather than the *N × M*
explosion that ruled out per-component blocks.

### 4.3 Punctuation belongs inside the message

`"Loading..."` is wrong in English (the character is U+2026 `…`) and building it
as `format!("{}...", t::common::loading(loc))` is wrong everywhere else: French
sets a narrow no-break space before `! ? : ;`, and Chinese uses `……` — two
full-width characters. **The whole string is the unit of translation, punctuation
included**, which is the same reason `pp-t` owns an element's entire text content
(§5.1) rather than interpolating into surrounding literal text.

Relatedly, keys are **per usage context, not per English string**. `common.loading`
as a button label and as a full-page state may need different translations in a
language that inflects; if two usages could ever diverge they are two keys with
translator comments. Sharing by identical source text is Lingui's generated-ID
failure mode arriving through the back door.

## 5. Author surface

### 5.1 Templates — `pp-t`

`pp-t` owns the element's text content, exactly as `pp-text` does, because a
translator never translates half a text node. Arguments ride the existing
head-vs-arg directive syntax already used by `pp-bind:attr`, `pp-on:event` and
`pp-model:prop`, so there is no new grammar to learn:

```html
<p pp-t="cart.items_in_basket" pp-t:count="cart.len"></p>
```

```json
// locales/en.json
"cart.items_in_basket": "{count, plural, =0 {Your basket is empty} one {# item} other {# items}}"
```

Attributes take arg-less messages through a `$t` magic path, joining the existing
`$store` / `$route` / `$event` surface and needing no new expression syntax
(`Expr::Path` already handles it):

```html
<input :placeholder="$t.auth.email_placeholder" :aria-label="$t.auth.email_label">
```

`$t` is the **only** attribute form — there is no `pp-t@placeholder`. Attribute
messages are overwhelmingly placeholders, titles and aria-labels, which take no
arguments; the rare arg-taking case goes through a computed field calling the
generated function, rather than growing a second directive syntax for it.

Messages containing markup use **positional element placeholders**, matched to
the element's child elements in source order:

```json
"legal.tos": "I accept the <0>terms</0> and <1>privacy policy</1>."
```

```html
<p pp-t="legal.tos">
  <a pp-route href="/terms"></a>
  <a pp-route href="/privacy"></a>
</p>
```

This is the only model that survives a translator **reordering the clauses**,
which they will do routinely and which splicing `{{ }}` fragments cannot express.

### 5.2 Rust — generated functions, locale always explicit

```rust
// generated into OUT_DIR from locales/en.json, mirrored as a module tree.
// Plural args arrive as CLDR operands, never a bare integer — see §6.4.
pub fn items_in_basket(loc: Locale, count: PluralArg) -> String;

// call site: locale was supplied by the caller.
let label = t::cart::items_in_basket(locale, cart.len().into());
```

`PluralArg` carries the CLDR operands `(i, v, f)` — integer digits, visible
fraction digits, fraction value — with `From<i64>`/`From<u64>` for the common
integer case and an explicit constructor for decimals. §6.4 shows why a bare
`i64` is not enough: it cannot express the difference between Spanish's
`one: n = 1` (where `1.0` is singular) and English's `i = 1 and v = 0` (where it
is not), and widening the signature later would break every generated call site.

Codegen rather than a `t!()` macro, so rust-analyzer completion, go-to-definition
and doc hover work with no expansion. Arity and argument types come from the
default locale's parsed AST, so a wrong argument is a type error.

**The locale is always the first argument.** No thread-local, no task-local, no
ambient default. RFC-119 exists because authority that travels implicitly gets
silently dropped by internal calls, and a request-scoped locale on a server is
precisely that kind of authority. The component reads its reactive locale at
the client boundary; the server handler receives a negotiated `Locale` through
a typed request extension. Both pass the resulting value to generated functions
and downstream services. There is no zero-argument server `i18n::locale()`
accessor; workers take the locale from their explicit input (§5.5).

### 5.3 Getting the catalog there in time (client-only mounts)

Under SSR this section is moot — the server stamped the text and the catalog is
only needed for later re-renders. On a pure client mount it is a real concern,
and **it is only a non-issue if the shell issues the fetch, not the wasm.** If
the wasm requests its catalog on boot there is no race at all, just a serial
dependency: the request leaves one RTT *after* the app is ready to render, which
is precisely the worst moment.

Three mechanisms, all small, none in the reactive runtime:

1. **Preload from the HTML shell.** The build emits a locale → fingerprinted-URL
   map into the document plus a short classic script that resolves the locale
   from the §8 chain and appends `<link rel="preload">`. Classic scripts run
   before the deferred module boot, so the fetch is genuinely parallel with the
   wasm download. This is the pattern `pocopine-cli/assets/loader.js` already
   establishes. A static SPA serves one `index.html` for every route, so the
   locale is resolved inline rather than hardcoded at build time — hardcoding the
   default would leave exactly the non-default users paying the serial cost.
2. **Gate the splash on both signals.** The boot loader already owns splash
   dismissal; gate it on wasm-ready *and* catalog-ready. A late catalog then
   shows the wordless splash slightly longer instead of a laid-out page with
   blank text, which is the genuinely ugly failure.
3. **Atomic swap on runtime locale change.** Choosing a locale from a menu is the
   one case that cannot be preloaded, so `set_locale()` resolves the catalog
   *before* flipping the signal. Text lingers in the old language a beat rather
   than emptying. **The locale signal must never lead its catalog.**

With those in place a missing catalog should be unreachable, but `pp-t` still
needs defined behaviour, following RFC-099's divergence policy: **dev renders the
key** (`⟦common.loading⟧` — visibly wrong and greppable), **prod renders empty**
and fills when the catalog lands.

Sizing, for calibration: a small catalog is single-digit KB gzipped, but two
thousand messages is nearer 20 KB. Still an order of magnitude under the wasm, so
the parallel fetch always wins — the preload matters *more* as the catalog grows,
not less.

The *pre-wasm* phase needs nothing at all: the CLI's boot loader is a logo and a
progress bar with `alt=""` and no text
(`pocopine-cli/src/build.rs::inject_loader`). The string an app most needs before
anything has loaded is "Loading…" — and pocopine's splash is wordless, so the
bootstrap problem this would otherwise create does not exist.

### 5.4 Reactivity

`Locale` is a signal. `pp-t` installs one effect per bound node — the same shape
`directives/interp.rs` uses today: create the text node, bind an effect,
`track_effect_on(parent, id)` so release follows the existing unmount path.
Switching locale therefore re-renders bound text **without remounting anything**.

### 5.5 Server errors and messages to users

**Host translation is a first-class use case, independent of SSR.** HTTP and
streaming server functions, form validation, action confirmations, emails, and
notifications use the same catalog keys and generated Rust functions as the
client. A worker can depend on the locale runtime without `pocopine-core`, a DOM,
a router, or a running web server. This RFC provides message formatting and
locale propagation; delivery remains the application's mail/notification/job
integration.

**Resolve at the boundary, then pass explicitly.** HTTP integration negotiates a
supported `Locale` and attaches it to request extensions before locale-aware
request rejection or application code runs. Existing `RequestContext` and
`Extension<T>` in `pocopine-core/src/server.rs` provide the integration point;
handlers extract `Extension<Locale>` and pass its value to services. RPC client
stubs must forward the committed UI locale as explicit request metadata, since a
server-function endpoint need not contain the page's locale prefix. The explicit
preference wins over passive cookie/header detection; an absent or unsupported
preference follows the configured negotiation/fallback policy. RPC calls never
redirect to a locale-prefixed page. Locale chooses presentation only and does
not affect authentication, authorization, or error classification. A streaming
call keeps its negotiated locale for the lifetime of the stream.

**Translate the public message at the response boundary.** Domain services keep
typed errors and stable application codes; the response adapter selects the
corresponding generated translation function. Validation field identifiers,
error categories/codes, and retry decisions stay independent of translated text.
Raw diagnostic `Display` output is not a translation key or a public message.
For example, once the handler has an explicit locale and host catalogs are ready:

```rust
// Proposed generated function; the existing ServerError variant is unchanged.
let message = t::auth::invalid_credentials(locale);
let error = ServerError::unauthorized(message);
```

Today `ServerError` carries string payloads in `App`, `Unauthorized`, `Forbidden`,
and `BadRequest`; `Network` is synthesized by the client. The host variants can
carry translated public text while retaining their classification. Their
`Display` implementation adds English diagnostic prefixes, so user-facing UI
must consume the public payload, rather than display `error.to_string()`.
Application-specific machine codes remain in the application's typed response
contract; any richer framework error envelope needs a compatible wire design
before implementation, not an implicit change to these existing variants.
Framework-generated authentication, authorization, and malformed-request
rejections also need catalog-backed public messages, including rejections before
the handler body runs. Client-generated network failures use the client locale.
Unexpected internal failures map to a generic public message, with the original
cause retained in diagnostic logs. Clients display server-rendered messages as
received; they do not attempt to translate the resulting prose again.

**Outgoing messages use the recipient's locale.** A message to another user uses
that recipient's explicit or stored preference, falling back through the same
configured locale policy. It must not inherit the initiating user's language.
Resolve and snapshot the effective locale when creating the delivery job; include
it in the application's typed job payload, separately for each recipient. Retries
keep that locale. For scheduled messages intended to use a preference current at
send time, resolve it once when creating the delivery job from the schedule, then
keep it across retries. The worker never reads request-local or process-global
locale state. Date/time messages also need an explicit timezone policy; a
language tag does not identify the recipient's timezone.

Durable jobs store semantic message kind and typed arguments, not build-local
dense message IDs (§7.2). A worker maps that kind to its generated functions, so a
queued job survives deployment of a different catalog build. Locale snapshots
preserve the selected language, not exact wording across deployments; delivery
requiring exact wording must retain the rendered content or its catalog version.
Email subjects and text bodies use normal messages. HTML email composition owns
markup and escaping, following the same template-owned markup rule as §5.1.

**Host catalogs are ready before serving requests or executing jobs.** The host
loads and validates compiled catalogs against its build ID at initialization,
then shares immutable catalog data; there is no JSON/MF1 source parsing or
catalog fetch per request. Missing/corrupt required catalog artifacts fail
initialization. Missing translations within valid catalogs use the shared
fallback policy. Extraction includes host-only Rust message references so worker
messages survive pruning. Host-required catalogs are packaged with the server
or worker, without making host-only message contents browser assets. Target
reachability and catalog layout must preserve the build-ID/ID mapping contract
in §7.2; browser reachability alone cannot determine host catalog contents.

Acceptance checks for this slice include concurrent requests in different
languages without cross-talk; translated application and pre-handler failures
with unchanged error classification; a standalone worker formatting without a
browser; per-recipient locale propagation across retries; deployment across a
queued job; and host-only messages available without browser delivery. These
checks are independent of the SSR hydration parity gate.

## 6. SSR parity — the load-bearing section

### 6.1 What is free, and what is not

`js-sys` 0.3 already binds `Intl::PluralRules`, `NumberFormat`, `DateTimeFormat`,
`RelativeTimeFormat`, `ListFormat` and `Collator`. The wasm client gets full CLDR
formatting for **zero bundle bytes** — an advantage every JS i18n library leans
on and that pocopine inherits for free.

The server has no `Intl`. Its equivalent is ICU4X 2.x (`icu_plurals`,
`icu_decimal`, `icu_datetime`) with baked data sliced to the configured locale set.

These are **different ICU implementations at different CLDR versions**, and
browsers disagree with each other as well. RFC-099 §4 already names this class of
problem as *the gating risk* and solved its JS-number instance by writing one
pure-Rust formatter. i18n reopens it at CLDR scale, where "write one formatter"
is not available.

### 6.2 The split

| kind | decides | implementation | hydration |
|---|---|---|---|
| `plural` / `select` category | **which subtree exists** — structural | **one generated CLDR rule table, linked into both server and client**; `Intl.PluralRules` banned, and ICU4X is *not* shipped either (§6.4) | identical by construction; carried on the RFC-094 anchor label like any other decision |
| `number` / `date` / `time` / list rendering | **text** | server: ICU4X · client: `Intl` | server output is authoritative and **claimed**, not re-derived, until the value changes |

The cut is principled, not a compromise. A plural category selects a variant —
the same class of structural decision RFC-094/099 already labels on comment
anchors, and structural decisions must agree, so both sides run the same code.
Rendered numbers and dates are text, and RFC-099 already claims text without
re-deriving it; a value that never changes never re-renders, so the two
formatters never get the chance to disagree. When the value *does* change, the
client re-renders with `Intl` and is locally consistent from then on.

**Escape hatch, not a mode matrix:** a project-level `strict_parity` flag routes
all formatting through ICU4X on both sides. Byte-parity guaranteed, wasm bytes
spent. Off by default.

### 6.3 Cost — mostly already paid, on PR #209

An earlier draft called the differential harness "the largest single line item in
the feature." It is not, because RFC-099 phases 1 and 2 are **implemented** and
waiting on PR #209 (`feat/rfc-099-ssr-phase2`). What already exists:

| primitive | where | what it gives this RFC |
|---|---|---|
| `js_number::to_js_string` | `pocopine-core/src/js_number.rs` | one pure-Rust formatter shared by both sides, 2M-case round-trip fuzz |
| `host_eval` | `pocopine-core/src/host_eval.rs` | the same expression AST evaluated over `serde_json::Value`, 6k-case cross-engine differential fuzz |
| the stamper | `crates/pocopine-ssr` | plan → HTML string, per-directive string semantics mirroring the client |
| the byte-equal gate | `pocopine/tests/ssr_hydration.rs` | render server-side, hydrate, assert `outerHTML` identical before and after |

So the remaining cost is **extending an existing harness with a CLDR corpus**,
not building one.

**SSR does not gate this RFC.** It gates exactly one slice — stamping translated
text server-side and claiming it on hydrate. The catalog compiler, the MF1
formatter, the generated plural table, `pp-t`, `$t`, locale routing, switching
and catalog delivery are buildable independently, as is host-side formatting
for errors and recipient messages (§5.5). More pointedly, **the parity problem in this section does not exist without SSR**:
with no server-rendered text there is no second opinion to disagree with, and
§6.2 is a guarantee that only begins to be exercised once SSR ships. The
formatter is verifiable on its own terms meanwhile — unit tests plus the ICU4X
oracle, both host-side.

The order that follows is **shared formatter and catalogs first**, with client
bindings and server-message consumers independent of SSR. A client-only app and
a standalone worker must both be supported before server stamping is added.
Adding `pp-t` to the stamper afterwards is additive, one case beside the `pp-text` / `pp-bind` / `{{interp}}` cases it already handles. The one
constraint to honour from the start is that message resolution stays **pure over
`(locale, message id, args)`** with no browser assumptions, so the server can
call the identical code path — which is a design rule, not a scheduling one.

**Why `js_number`'s answer does not generalise — the question a reviewer will
ask.** RFC-099 solved "same text for same value" by writing *one* pure-Rust
formatter used by client and server alike, which is exactly the shape §6.2 uses
for plural selection. The reason it cannot also be used for locale-sensitive
number and date rendering is data, not principle: `js_number` implements JS
`String(n)` semantics, which are **locale-independent** and therefore a few
hundred lines with no data table behind them. Locale-*sensitive* formatting is
CLDR data — measured at 25.7 KB gzipped for decimal and 217 KB for datetime
(§6.4). One shared formatter stays the right answer wherever the rules are small
and closed; it stops being affordable exactly where CLDR data starts. Plural
rules fall on the affordable side, which is why they get the `js_number`
treatment and datetime does not.

### 6.4 Measured: plural rules are generated, not linked from ICU4X

Measured 2026-08-15 on `wasm32-unknown-unknown`, `icu 2.3.0`, rustc 1.95-nightly,
under pocopine's exact `[profile.release]` (`lto=true`, `codegen-units=1`,
`panic="abort"`, `opt-level="z"`), then `wasm-opt -Oz`. Figures are **marginal
over an empty cdylib baseline**, with the locale supplied as runtime bytes so
nothing const-folds.

| variant | Δ raw | Δ gzip | vs generated |
|---|---:|---:|---:|
| **generated CLDR table, 8 locales** | **3,458 B** | **1,926 B** | **1×** |
| `icu_plurals`, locale const at compile time | 41,271 B | 19,890 B | 10.4× |
| `icu_plurals`, locale resolved at runtime | 48,819 B | 21,814 B | 11.4× |
| `icu_decimal` | 55,848 B | 25,732 B | 13.5× |
| `icu_datetime` | 714,921 B | 216,864 B | 113.7× |

Three findings, each of which changes a decision:

**1. Data-slicing is the wrong lever for plurals.** Section split of the
`icu_plurals` build is **CODE 37,616 B (76.6%) / DATA 11,007 B (22.4%)** — the
CLDR plural data for *every* locale is only ~11 KB, and the cost is the ~37.6 KB
of machinery around it (locale parsing, fallback chain, zerovec/zerotrie
deserialization, the rule interpreter). `icu4x-datagen` and the runtime blob
provider can only touch the 11 KB. **Plan B from the previous draft is dead** —
slicing data cannot fix a code-dominated cost.

**2. The generated table wins by 11× and barely grows per locale.** 8 locales
covering all six CLDR categories — en, de, fr, es, ru, pl, ar, ja, including the
Slavic three-way and Arabic's full six — cost 1.9 KB gzipped, of which only
**713 B is the table itself**; the rest is shared code a real build already pays.
Adding a locale is one table entry and, usually, no new rule at all.

**3. Ship the same table on both sides.** Since the table is generated once at
build time and linked into the server and the wasm alike, plural selection is
identical **by construction** rather than by two implementations agreeing. This
is strictly better than the previous draft's "ICU4X on both sides", and it means
**ICU4X is not a runtime dependency at all** — it moves to the test suite, where
size is free.

**ICU4X's real job here is oracle, not runtime.** A host-side differential test
compares the generated table against `icu_plurals` across the configured locales.
This is not theoretical: the first hand-written version of the table used in this
measurement produced **42 mismatches across 2,664 cases** — 41 in Arabic (whose
rules operate on `n`, so any non-zero fraction is `other`) and 1 in Spanish
(`one: n = 1`, so `1.0` is `one`, unlike English's `i = 1 and v = 0`). Both were
found in seconds and both are exactly the class of error a hand-maintained table
invites. After correction: 2,664/2,664 match. **The oracle test is therefore not
optional — it is the thing that makes generating the table safe.**

**Corollary — §11.6 is answered.** Both bugs above were caused by a signature
that could not express the CLDR operands. `count: i64` is insufficient; the
generated functions need at least `(i, v, f)` — integer digits, visible fraction
digits, and fraction value. This costs nothing in the generated approach and must
be in the signature from day one, because widening it later is a breaking change
to every generated call site.

**Corollary — `strict_parity` is an escape hatch, never a default.** ICU4X
datetime is 715 KB raw / 217 KB gzipped (83.5% data), ~114× the entire plural
subsystem. Routing date rendering through ICU4X on the client to buy byte-parity
is not a trade anyone should make by default; the claim-don't-re-derive rule in
§6.2 is what makes it unnecessary.

> Harness: `scratchpad/icu-size/` (workspace of one baseline + five variants +
> the oracle binary). Should be landed under `tools/` or as a size-regression
> test before this RFC is implemented, so the numbers stay honest.

## 7. Build pipeline

This is `stylekit::project::compile_project` with a different payload — discover
sources, extract, dedup, compile deterministically, diagnose in file order — and
should reuse its diagnostics and span machinery rather than growing a second one.

```
sources (.poco + .rs) ──extract keys──┐
                                      ├─ validate ─┬─ missing in DEFAULT   → ERROR
locales/*.json ──parse MF1 → AST──────┘            ├─ missing in a locale  → warn + fall back
                                                   ├─ arg name/type drift  → ERROR
                                                   └─ ok → assign dense msg ids
                                                            → codegen + one message catalog per locale
```

### 7.1 No message bytes in the wasm (binding invariant)

> **Wasm size is independent of locale count and of catalog size.** Adding a
> locale adds an asset, never a byte of wasm. Adding a message adds a byte to N
> catalogs, never to the wasm.

An earlier draft baked the default locale into the wasm. That is wrong twice
over: every non-default user downloads a catalog they will never read, and the
wasm stops being one binary cacheable across all locales.

It is also unachievable by imitation. Paraglide gets constant bundle size because
its messages are ESM functions that Rollup eliminates when unreferenced. In wasm,
`pp-t="cart.items"` is a runtime string key, so the catalog must be reachable as
data and LLVM retains all of it — the generated Rust functions tree-shake, the
template surface does not.

The lever pocopine has instead is that **`pp-t` keys are literals the macro
already reads at compile time**. Extraction assigns each *referenced* key a dense
integer id, and every surface compiles to that id:

```
  pp-t="cart.items"        ──compile──▶  msg(42)
  $t.auth.email            ──compile──▶  msg(17)
  t::cart::items(loc, n)   ──compile──▶  msg(42)

  message catalog per locale = positional array, not a map
    en  [ …, 42: "{count, plural, one {# item} other {# items}}", … ]
    fr  [ …, 42: "{count, plural, one {# article} other {# articles}}", … ]
```

No key strings in the wasm, no hash map in the wasm, and a key that nothing
references never gets an id — so it ships in **neither** the wasm nor any
catalog. This is real tree-shaking on both sides, paid for by an extraction pass
that already walks every `.poco` and `.rs`.

**The constraint that buys it:** message keys are static literals. There is no
dynamic-key form — no `:pp-t="expr"`. Angular, Lingui and Paraglide all require
this for extraction; it is recorded here as non-goal #8 rather than discovered
later.

What remains in the wasm, honestly:

| stays | grows with catalog? | grows with locale count? | measured |
|---|---|---|---|
| MF1 formatter | no | no | — |
| `pp-t` binding machinery (one effect per node, as `interp.rs`) | no | no | — |
| generated plural-rule table | no | yes, **~90 B/locale** | 713 B for 8 locales (§6.4) |
| message strings | — | none present | 0 |

The plural table is the only part that grows with locale count, and §6.4 measures
that growth at roughly ninety bytes per locale — small enough that the invariant
holds in practice. Had ICU4X been linked instead, this row would have read 48.8 KB
flat, which is why it is not.

**Strings or pre-parsed segments in the catalog?** The same tradeoff templates
already settled deliberately (`include_str!` + a runtime parser): the parser
lives in the wasm once, cached and locale-independent, while the catalog stays
small and only one of them is ever downloaded. Ship raw ICU strings. The parsed
shape is close enough to `directives::interp::PlannedSegment` that the two should
probably share a representation.

### 7.2 Delivery

The compiled per-locale catalog is a **positional array indexed by message id**,
not a map: every locale's array has the same length and the same index meaning,
so switching locale is swapping which array `msg(n)` reads. No keys appear inside
it, and lookup is an index rather than a hash probe.

v1 is a fingerprinted asset per locale — cached across navigations, fetched in
parallel with the wasm, and swapped on a locale change.

**Version-locking is a correctness requirement, not a caching nicety.** Because
ids are positional and assigned at build time, a wasm binary and a catalog from
different builds are silently incompatible: if a key's index shifted between
deploys, a stale catalog does not fail to resolve — it renders *the wrong message
in the right place*, which is worse than an error. Filename fingerprinting alone
does not close this, since a cached HTML document can point a new wasm at an old
catalog URL. The build therefore stamps a **catalog build-id into both the wasm
and every catalog**, the loader compares them before the first `msg()` resolves,
and a mismatch is a hard refetch — never a best-effort render. Under SSR the same
id is emitted on the state island so a stale document is caught on hydrate. Under SSR the strings can
instead ride the document as a JSON island beside RFC-099's state islands, which
removes the round trip but is not cached across navigations, so it only pays off
once the payload is sliced per route. That slicing is the same mechanism the
two-tier template plan needs, which resolves §11.4: **one mechanism, not two.**

## 8. Routing

`prefix-except-default` is the default: `/pricing` serves the default locale,
`/de/pricing` serves German. Search engines crawl without cookies and with
`Accept-Language: en`, so a cookie-only site is monolingual to a crawler; the URL
must be the source of truth for anything indexable.

- Locale is a route segment, resolved before the loader runs.
- `Accept-Language` seeds only the **first** visit's redirect.
- A cookie stores an explicit user override and is never authoritative.
- The SSR shell emits `<html lang>`, `dir`, `hreflang` alternates and `x-default`.
- Detection is an inference; an explicit picker always wins.

## 10. Non-goals (binding)

1. **No second message format.** ICU MF1 subset only; MF2 arrives as a parser
   swap, never as an option. No Fluent backend, no format plugins.
2. **No runtime parsing of catalogs at request time** — the parallel of RFC-099
   non-goal #4. Catalogs are compiled artifacts.
3. **No ambient locale.** `Locale` is an explicit argument in Rust.
4. **No `Intl.PluralRules`, and no ICU4X in the shipped runtime.** Category
   selection is structural, so it runs off one generated table linked into both
   sides (§6.4). ICU4X stays in the test suite as the oracle and on the server
   for number/date *rendering* only.
5. **No per-locale builds** (Angular's model) — incompatible with one wasm
   artifact plus SPA routing.
6. **No machine translation and no TMS API integration in-tree.** Files in, files
   out; the TMS is the user's business.
7. **No RTL layout system.** `dir="rtl"` on the shell is in scope; logical-property
   utilities belong to Stylekit if they land at all.
8. **No dynamic message keys.** Keys are static literals at every surface. This
   is what makes §7.1's invariant reachable; a single `:pp-t="expr"` would drag
   the entire catalog back into the wasm.
9. **No template pipes.** Angular-style `{{ x | date:'short' }}` is deliberately
   not adopted: `Expr::Call` already exists, so pipes would buy postfix syntax
   rather than capability, and `@Pipe`'s registry is the extension protocol this
   codebase does not build. Angular's own motivation is also absent — pure pipes
   memoize against whole-template change detection, and fine-grained effects
   re-run only the binding that changed. If chaining ever reads badly in
   practice, `a | f:b` is pure sugar over `f(a, b)` and can be added later
   without breaking anything.

**Formatting a bare value outside a message** (a raw `{{ order.total }}`) is
consciously left to a **follow-up**: a closed table of builtin functions resolved
by the runtime ahead of `invoke_handler` — the same shape as the existing
`$`-prefix guard in `Expr::Call` — rather than methods on every component, which
would grow each generated handler match, conflate pure transforms with
state-touching callbacks, and have no locale to work from (`uppercase` is
locale-sensitive: Turkish `i` uppercases to `İ`). Anything with words around it
goes through a message instead, since where a currency symbol sits is a
translation decision. **That follow-up must land after this RFC**, or it would
need its own reconciliation of browser-vs-server formatting and produce the
second divergent formatter §6 exists to prevent.

## 11. Prior art: `leptos_i18n`, and where this diverges

The closest existing design in Rust, and the one to measure this against. What it
does, from its own book and feature list:

| dimension | `leptos_i18n` | this RFC |
|---|---|---|
| files | JSON/YAML per locale, **namespaces + inheritance** | JSON per locale, module-path namespaces (no inheritance — §11.7) |
| interpolation | `{{ var }}` | ICU `{arg}` |
| plurals | **i18next key suffixes** — `items_one` / `items_other`, merged into one key; `_ordinal` variants | inline ICU `{count, plural, …}` |
| markup in messages | **arbitrary HTML-ish tags inside the string**, with attributes and variables (`highlight <b id="john">me</b>`) | positional `<0>…</0>` only; markup stays in the template |
| codegen | typed API per key; keys, interp args and locale set all compile-checked | same guarantee, via dense message ids |
| call site | `t!(i18n, items, count = \|\| n)` — args are closures | `t::cart::items(loc, i, v, f)`; template `pp-t:count=` |
| plural engine | ICU4X shipped to wasm (`icu_compiled_data`, **on by default**) | generated CLDR table on both sides (§6.4) |
| locale resolution | URL prefix (`I18nRoute`) → cookie → `Accept-Language` (SSR) → `navigator.languages` (CSR) → default; **server always resolves under SSR** | same order (§8) |
| locale in server fns | `resolve_locale()` — **implicit** | explicit `Locale` argument (§5.2) |

### 11.1 Where it validates this design

Two convergences are worth stating because they were reached independently.
Locale resolution order is effectively identical, including "the server always
resolves under SSR and the client does not recompute on load." And `dynamic_load`
does exactly what §7.2 proposes: *"the server will register every unit used for a
given request and bake only the used one in the sent HTML,"* parsed during
hydration so the first paint issues no translation request.

### 11.2 Where its own documentation is evidence against copying it

**1. Per-key codegen makes the binary grow with catalog size.** `dynamic_load`
removes baked strings, but the book states the limit plainly: *"Only the raw
strings are removed from the binary; the code to render each key is still baked
in it, whatever the locale or the namespace."* That is precisely the invariant
§7.1 forbids. It follows from generating a rendering path per message; compiling
keys to dense ids and interpreting one MF1 string with one formatter makes the
code O(1) in message count instead of O(keys). **This is the single strongest
argument for the shape in §7.1, and it is an admitted limitation rather than an
inference.**

The honest cost of the divergence: a generic interpreter marshals arguments
through a value array rather than emitting a direct call, so it is marginally
slower and marginally less "zero-cost" per render. Compile-time argument checking
is unaffected — the generated signature still carries the types.

**2. ICU4X-by-default pushes a manual optimization ritual onto the user.** The
book's own numbers: the plurals example is **394 kB**, dropping to **248 kB**
after datagen — a saving it recommends in capital letters as "Worth the Trouble."
Earning it requires disabling `icu_compiled_data`, running `icu_datagen`,
implementing a provider struct, and calling `set_icu_data_provider()` in *both*
hydrate and server startup. §6.4 measures why that ritual should not exist for
plurals at all: the cost is 76.6% code, so datagen can only touch the data
quarter. Generating the rule table removes the workflow rather than documenting
it. (Their `leptos_i18n_build`, which parses translations to infer exactly which
ICU data markers are needed, is a genuinely good idea worth borrowing **on the
server**, where datetime data is data-dominated and size is free anyway.)

**3. Implicit locale resolution produces a documented ordering bug.**
`resolve_locale()` reads ambient state, and the book carries the consequence as a
caveat: URL-prefix detection *"only activates when the `I18nRoute` component
renders,"* so *"code executing before that point may reference an incorrect
locale."* That is the RFC-119 failure mode exactly — authority that travels
implicitly gets silently read at the wrong time — and it is why §5.2 makes
`Locale` an explicit argument and §8 resolves it at route-match time, before
loaders run.

### 11.3 Where their choice is defensible and this RFC simply forks

**Plural declaration.** Key suffixes (`items_one` / `items_other`) read better in
a diff and are what i18next tooling and the `i18n Ally` VSCode extension already
understand. Inline ICU keeps one key equal to one message, which is what XLIFF and
TMS round-tripping assume (§9). Both handle locale asymmetry correctly — a Russian
file supplies four forms either way. This RFC picks inline ICU for the export
path; the suffix form is a legitimate alternative, not a mistake.

**Markup in messages.** Their form is more expressive: real tags, attributes, even
variables inside attributes. It also means the translation string is a
mini-template that can introduce markup and attributes the reviewer never saw,
which is an authoring and injection hazard, and it makes the message untranslatable
by tools that expect text. Positional `<0>` keeps every tag and attribute in the
template where review happens and lets the translator control only ordering —
which is the part they actually need.

## 12. Open questions

1. ~~**ICU4X footprint on wasm32, measured.**~~ **Resolved — measured 2026-08-15,
   see §6.4.** `icu_plurals` costs 48.8 KB raw / 21.8 KB gzipped and is
   *code*-dominated (76.6%), so data-slicing cannot help. A generated CLDR table
   is 11× smaller, ships on both sides for parity by construction, and moves
   ICU4X to the test suite as an oracle. What remains open is only **who
   regenerates the table when CLDR ships new rules** — a vendored snapshot with a
   CI job that diffs against the current `icu_plurals` is the obvious answer, but
   the cadence and ownership need naming.
2. ~~**`$t` magic vs an attribute-target form of `pp-t`.**~~ **Resolved — `$t`
   only.** `$t.auth.email` needs no new expression syntax (`Expr::Path` already
   handles it) and joins the existing `$store` / `$route` / `$event` surface
   rather than growing a second directive form. Arg-taking attribute messages —
   rare, since attributes are overwhelmingly placeholders, titles and aria-labels
   — go through a computed field calling the generated function. `pp-t@attr` is
   dropped.
3. ~~**Key ↔ module coupling.**~~ **Resolved in §4.1 — enforced, with `common.*`
   as the single shared namespace.** Convention alone permits accidental
   cross-module reuse that stays invisible until one module's copy changes and
   another silently changes with it.
4. ~~**Shared mechanism with two-tier templates.**~~ **Resolved in §7.2: one
   mechanism.** Both are compiled artifacts the server can deliver pre-resolved
   and slice per route. What remains open is only the *sequencing* — does locale
   slicing wait for RFC-099 phase 4, or can the flat per-locale asset ship first
   and adopt slicing later? (Spec assumes the latter.)
5. ~~**Crate boundary for `Locale`.**~~ **Resolved — `pocopine-locale` is a leaf
   crate and owns it.** The earlier answer (put `Locale` in core) existed only to
   stop core depending on an app-level crate; that constraint dissolves once the
   crate is a dependency-free leaf that core and `pocopine-server` both consume.
   A crate called `pocopine-locale` that did not contain `Locale` would have been
   its own bug. Extraction and codegen are host-gated inside it via the
   `client-server-modules` pattern.
7. **Locale fallback chains — a gap this spec currently has.** §7 says a missing
   translation "falls back to the default," which is too blunt. `leptos_i18n` has
   explicit *inheritance*, and CLDR defines a parent chain, so `fr-CA` should fall
   back to `fr` before reaching `en`. Adopt the CLDR parent chain, or a declared
   per-locale parent in `pocopine.toml`?
8. **Ordinals.** §2 excludes `selectordinal` from the subset, but `leptos_i18n`
   ships `_ordinal` because "1st / 2nd / 3rd place" is a real requirement. Ordinal
   plural rules are the same shape as cardinal ones and would ride the same
   generated table at roughly the same cost. Reconsider for v1?
6. ~~**Plural argument typing.**~~ **Resolved in §6.4 — integer-only is not
   acceptable.** Both bugs the oracle caught traced to missing CLDR operands
   (Arabic needs the fraction value; Spanish's `n = 1` differs from English's
   `i = 1 and v = 0`). The generated signature carries `(i, v, f)` from day one;
   widening it later would break every generated call site.
